Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, SearchCriteriaDisplay, PersonListPanel, SidePanel and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects and structured search criteria.

MainWindow lays out two columns. The left one holds the CommandBox, ResultDisplay, SearchCriteriaDisplay and PersonListPanel, and keeps at least 450 px so that cards still wrap whole words. The right one is the SidePanel, at least 300 px wide, which shows one long output at a time: the HelpPanel after help, the ProductSummaryPanel while it is visible during a product search, and the DeliverySummaryPanel otherwise. MainWindow shows help when a CommandResult asks for it, and returns the panel to the summaries after the next successful command. A window narrower than 900 px gets the :compact pseudo-class, which DarkTheme.css uses to tighten the gaps around the customer list.

MainWindow owns one SearchCriteriaDisplay, places it above the customer list and supplies Logic.activeSearchCriteriaProperty(). The display renders the current value immediately and observes criteria changes directly, including searches with identical results. It delegates formatting to SearchCriteriaFormatter, which creates an immutable SearchCriteriaSummary. The display uses the summary's heading and complete criterion labels to render its badges in predictable order. These dependencies are shown with dashed arrows in the UI diagram. Formatting stays separate from matching and does not parse diagnostic toString() output.

PostalCodeCriterion.getPostalCodePrefix() exposes the immutable search digits for a Postal badge, preserving leading zeros and the supplied prefix length. Postal badges are ordered after Address and before Tag badges.

ItemCriterion exposes its stripped display product name and immutable accepted statuses. The formatter keeps the capitalization typed by the user and both conditions in one Item badge after customer badges, reflecting same-item matching. All statuses on a product criterion display as Any status; subsets display their readable labels joined by or in fulfilment order. A criterion without a product uses Item status, retaining the status-only search and tracking labels. An empty status set displays None, so a criterion matching no items is still visible.

FulfilmentDateCriterion.getDate() and FulfilmentMethodCriterion.getMethod() expose their immutable matching values. Date badges reuse FulfilmentDate.toDisplayString() for English dates such as 22 Oct 2026; method badges show Delivery or Collection. Handover-note badges use the normalized query from TextContainsCriterion. The complete display order is Name, Phone, Email, Address, Postal, Tag, Item (or Item status), Date, Method and Handover notes, independent of prefix order or the model's unordered criteria set.

The display uses a FlowPane of read-only labels. Badges wrap onto additional rows without a row limit, and each badge is limited to the available width so long values wrap inside it. Its preferred-height measurement also accounts for wrapping when FlowPane measures a row without supplying a width. Empty searches hide the badge container and show only Showing: All customers; active searches show Filters · Match all. No focus request is made during an update, and the display cannot receive mouse input or keyboard focus.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

If parsing fails, the parser throws a ParseException before returning a Command, so LogicManager does not execute the command. Field-specific parsing errors may be refined before they are thrown, as described in Prefix boundaries and error messages.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.

A confirm entered without a pending clear goes through normal parsing and produces the unknown-command message.

Prefix boundaries and error messages

ArgumentTokenizer recognizes only the prefixes supplied by a command parser, at whitespace boundaries. A supported prefix ends the preceding value. An unsupported prefix-like token stays in the current value or preamble. Here, a prefix-like token for diagnostic purposes is one or more ASCII letters followed by / after whitespace. The tokenizer preserves conventional c/o text inside an address instead of treating it as a postal-code prefix. Quotation marks and backslashes do not escape supported prefixes.

The following parsers refine errors from constrained fields using ParserUtil.createFieldParseException:

Parser Fields with contextual prefix diagnostics
DeleteItemCommandParser Item index (i/)
EditCommandParser Customer name (n/), phone (p/), email (e/) and postal code (c/)
EditItemCommandParser Item index (i/), quantity (q/) and status (s/)
TrackCommandParser Status (s/)
AddItemCommandParser Quantity (q/) and status (s/)
PreorderCommandParser Date (f/) and method (m/)
AddCommandParser Name (n/), phone (p/), email (e/) and postal code (c/)
TagCommandParser Tag (t/)
UntagCommandParser Tag (t/)
FindCommandParser Name (n/), phone (p/), email (e/), postal code (c/), tag (t/), date (f/), method (m/) and status (s/) queries

Each field is validated normally first. If parsing fails, the parser passes the failed value, exception, command word and supported prefixes to ParserUtil.createFieldParseException. This shared helper uses findUnsupportedPrefix to find the first token matching \s([A-Za-z]+/) whose prefix is absent from that command's supported-prefix list. It preserves the prefix's case and formats Messages.MESSAGE_UNSUPPORTED_PREFIX with the offending prefix and command name, for example Unsupported prefix 'd/' for track. If no unsupported prefix is found, the original field constraint message is used. An overload accepts a custom fallback for item-index errors. Both overloads retain the original exception as the direct cause. The helper scans only a failed constrained field's value. Since its pattern requires preceding whitespace, a token at the start of that value, or one embedded without a whitespace boundary, does not trigger this diagnostic; the field's normal constraint message is used instead. Customer-index and duplicate-prefix checks retain their earlier precedence.

EditCommandParser preserves its field-validation order: name, phone, email, address, then postal code. Customer names are constrained by Name and do not permit slashes. Address validation permits ordinary slash notation such as #04/08 and conventional c/o, but rejects a letter-based token followed by / at the start or after whitespace, such as s/pending or x/foo.

TagCommandParser and UntagCommandParser check the index format before calling ParserUtil.parseSingleTag with their format-error message and command word. This shared helper checks the required t/ prefix and duplicate t/ prefixes before calling ParserUtil.parseTag. Only a tag-value failure is passed to ParserUtil.createFieldParseException, so each command retains its own unsupported-prefix message.

This is an error-message refinement rather than a global rejection rule. Address validation allows ordinary slash notation and conventional c/o while rejecting a letter-based token followed by / at the start or after whitespace, which could be mistaken for another field. Item names, remarks and handover notes reject forward slashes through their model validation. Do not apply the helper to valid free-text values or scan the complete command before field validation. FindCommandParser uses the shared tokenizer too. It validates name, phone, email and postal-code queries using search-specific constraints, and validates tags, dates, methods and statuses through their existing validators. Each failed constrained value is passed to ParserUtil.createFieldParseException to refine its error. For example, find c/123 x/foo identifies x/ while find c/123 remains a valid postal-prefix search. Address, product and handover-note queries are parsed as text. Product and handover-note queries reject slashes, while address queries retain ordinary slash text, including c/o. Only the failed field's value is inspected, so find a/Block c/o Alice s/invalid still reports the status constraint rather than an error about the address. Unsupported arguments in the preamble are rejected by the existing nonempty-preamble check.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores each customer's preorder, if any, as a Preorder holding the Items they ordered (see Preorders and items).
  • retains one active SearchCriteria in ModelManager to select which customers appear in the filtered list (see Customer search criteria).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list, and shows them through a sorted view of that list. Model#getFilteredPersonList() returns the sorted view as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes. The sorted view keeps the saved order until sort date or group postal sets an order (see Sorting by fulfilment date).
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Customer search criteria

The seedu.address.model.search package provides reusable search predicates. FindCommandParser constructs a SearchCriteria from prefixed customer and item fields, and FindCommand applies it through the existing model filtering API.

ModelManager keeps the active immutable SearchCriteria in memory and uses it to filter the customer list. The criteria are observable so the UI can refresh search badges even when the same customers still match. Search criteria are not saved with customer data.

Each successful find or track replaces the active criteria. list applies SEARCH_CRITERIA_SHOW_ALL_PERSONS, an empty search, to reset the state and show every customer. Rejected commands leave the active criteria unchanged. find and track use the immutable ItemCriterion for item matching. It accepts a customer when any single item satisfies both its optional product name and accepted statuses. Customers without a preorder or with an empty preorder never match item criteria.

Customer changes preserve the active criteria and re-evaluate the affected customer. A new customer is displayed only if they match, and an edited customer disappears when they stop matching. Commands resolve their target from the displayed list, so subsequent commands must use the updated displayed indexes. Rejected updates preserve both criteria and results.

SearchCriteria combines zero or more PersonCriterion objects using AND, so a customer must match every criterion. An empty search matches every customer.

The following diagram shows the criteria structure and its current implementations:

TextContainsCriterion handles substring searches for names, phone numbers, email addresses, addresses and handover notes. Matching ignores case and surrounding whitespace while retaining internal spacing and punctuation. TagCriterion uses complete, case-insensitive tag matching. The parser applies search-specific validation to contact fragments; these rules differ from the validators used when saving complete contact details.

Date and method criteria inspect fields shared by the Preorder, independently of its items. Handover-note searches also inspect the preorder and never inspect item remarks. Missing preorders or missing requested fields do not match, but an empty preorder can match when it has the requested shared detail.

PostalCodeCriterion matches a one-to-six-digit prefix against the stored postal code. Leading zeros remain significant, and a six-digit query matches the complete code. Stored postal codes remain mandatory and add and edit require all six digits. Postal criteria combine with other conditions, so find n/Alice c/53 requires both a matching name and a postal code beginning with 53.

To add a new search condition, implement an immutable PersonCriterion and combine it in SearchCriteria. Keep CLI prefix parsing in FindCommandParser.

FindCommandParser combines d/ (PREFIX_DETAILS) and s/ into one ItemCriterion. Separate predicates for "has this product" and "has this status" would incorrectly allow different items to satisfy the conditions.

For find, omitting s/ means all item statuses. track uses a different default; see Tracking preorders for its status selection and feedback behavior.

Date, method and postal conditions remain separate customer criteria because they describe the preorder or customer rather than an individual item.

Preparation summary and matching-item highlighting

ProductPreparationSummary.from creates an immutable snapshot from the filtered customers and a product ItemCriterion. It reuses ItemCriterion.matches, retaining matching entries in customer/item order, including duplicates. Each MatchingItem retains its customer and original one-based item number for remark attribution. Customer count is distinct, item count counts entries, and the quantities of all matching items are summed into a long total quantity. Constructors reject null inputs and invalid item references; collections are defensively copied.

MainWindow puts ProductSummaryPanel in the SidePanel. The summary listens to both the filtered customer list and Logic.activeSearchCriteriaProperty(), so changing criteria refreshes it even when the same customers remain visible. Its criteria invalidation listener also refreshes the heading for capitalization-only changes, which are equal for filtering purposes. It is visible and managed only when a product criterion exists. Updates recompute the snapshot, including zero results. Labels wrap inside a focusable scroll pane, whose key handler supports arrows, Page Up/Down and Home/End with scroll values clamped to the valid range.

PersonListPanel also refreshes its cells when active criteria change. Each PersonCard receives the current criteria and reuses the item matcher to add the matching-item style, a yellow box. It keeps all items, original numbering and status styles. Status-only criteria (including track) also highlight matching items; criteria without item conditions produce no highlights. The customer list uses native JavaFX keyboard navigation and selects its first entry when focused without an existing selection.

Delivery preparation summary

DeliveryPreparationSummary takes a snapshot of the current displayed customer results. It reuses ItemCriterion with no product condition and statuses PENDING and PREPARED, then requires the preorder's method to be DELIVERY. It counts customers, not matching items. Collection, unset methods, empty wrappers and completed-only preorders are excluded. Dates and notes may be unset without excluding an otherwise outstanding delivery. The immutable snapshot orders contacts by postal code and name, without mutating the address book or the active search criteria.

MainWindow puts a DeliverySummaryPanel in the SidePanel. The panel observes the existing Logic.getFilteredPersonList() observable view and rebuilds its snapshot when results or customer records change. It reuses GroupPostalCommand.getPostalGroupKey for contact headings and FulfilmentDate.toDisplayString for dates. Names, phones, addresses, postal codes and shared handover notes are shown in a keyboard-scrollable area with wrapped text. Missing dates display Not scheduled; absent handover notes display Handover notes: None. The panel stays installed and visible when there are no outstanding deliveries, showing zero totals and No outstanding deliveries in the current results. The UI tests cover exclusion of ineligible preorders, one contact per customer with multiple outstanding items, postal headings, and layout at the minimum FXML window dimensions.

This adds a derived model snapshot and a UI part within the existing Model/Logic/UI boundaries. It does not introduce stored summary state or change the fulfilment fields, JSON schema, customer reconstruction, or grouping command.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Safe startup after a data loading failure

JsonUtil.readJsonFile reads the file directly and returns Optional.empty() only for NoSuchFileException. Other read failures, malformed JSON and a JSON null document produce DataLoadingException. A genuinely missing data/lebake.json retains the first-run behavior: load sample data and create the file after a successful command.

The JSON adapters report invalid fields through DataValidationException, a subtype of IllegalValueException. It carries a concise user message while preserving the detailed validation message and cause for diagnostics. JsonSerializableAddressBook adds the person's position, and JsonAdaptedPreorder adds the item's position. These positions start at 1 and follow the JSON list order. For example, the dialog can report Person 2: item 3: invalid quantity. The whole file is rejected at the first failure.

MainApp.init() remembers a loading failure and skips model, logic and main UI initialization. It allows the JavaFX lifecycle to reach start(Stage), which shows a standalone error alert containing the absolute file path, reason and recovery instructions. Malformed JSON errors include their line and column when available. Dismissing the alert invokes the exit callback, which defaults to Platform::exit, and stop() safely handles incomplete initialization. The saved data file is never written on this failure path.

MainAppTest covers normal and missing-file startup, failed initialization, dialog content and dismissal, safe shutdown, and preservation of existing file contents. It also checks JSON errors without a location and uses a recording exit callback to verify that shutdown is requested exactly once, after the dialog closes, without stopping the shared JavaFX runtime. DataValidationExceptionTest checks concise record context and preservation of detailed diagnostics. The packaged-JAR checks below verify the actual JavaFX process exit.

Customer field length validation

Name, Email, Address and Tag define MAX_LENGTH values of 100, 254, 300 and 30 respectively. Lengths use String.length() (UTF-16 code units). Names are trimmed and consecutive ASCII spaces collapse before validation. ParserUtil trims other command values; JSON adapters validate those strings as stored.

Constructors, ParserUtil, JsonAdaptedPerson and JsonAdaptedTag share the value classes' validators and getValidationErrorMessage(String). Oversized fields use MESSAGE_LENGTH_CONSTRAINTS; other invalid values use MESSAGE_CONSTRAINTS. Length takes precedence over format within a field, while command syntax checks may fail earlier. Parsers may refine either field error into an unsupported-prefix diagnostic. JsonAddressBookStorage wraps adapter failures in DataLoadingException, rejecting the whole file.

Text queries for names, emails, addresses, products and handover notes have no stored-field length limit. Phone queries accept one to eight digits. Tag queries use ParserUtil.parseTag and share the 30-character limit.

Automated tests cover N−1/N/N+1 across model, parser, command and storage layers, including normalization, UTF-16 counting and error precedence. Integration tests verify saving and reloading, and preservation of data, search state and saved JSON after rejected commands.

Preorders and items

A customer's preorder records the products they ordered and how they will be handed over. Each customer has at most one Preorder, and each Preorder holds the customer's Items in the order they were added.

  • Person stores its preorder as an Optional<Preorder>, which is empty for a customer without one.
  • Preorder keeps an unmodifiable copy of its items and may have none yet. The number shown before an item on the customer's card is its position in this list, starting from 1.
  • Preorder also has an optional FulfilmentDate, FulfilmentMethod (DELIVERY or COLLECTION) and HandoverNotes, such as "Call on arrival". They belong to the whole preorder, so all of its items are handed over together. Preorder#withItems() keeps them when a command changes the items.
  • Item has an ItemName of up to 200 characters, a Quantity, an ItemStatus, and an optional Remark. ItemName turns each run of spaces, including Unicode spaces, into one space, so Butter Cake and Butter Cake are the same product in find and the preparation summary. ItemName and Remark reject forward slashes, so a slash is refused in a command and also stops a data file from loading. A Quantity is a whole number from 1 to 999, and a Remark is a special request of up to 100 characters.
  • Every item has a quantity. The Item constructor rejects a null quantity, and the data file loader rejects an item without one (see Saving preorders).
  • ItemStatus belongs to each item, so a customer can have one item PREPARED while another is still PENDING. There is no overall status for a customer or a preorder. track matches a customer when any item has one of the requested statuses.

Preorder and Item are immutable. A command that changes a customer creates a new Person and replaces the old one through Model#setPerson. Commands that do this for other reasons, such as edit, tag and untag, pass the existing preorder to the new Person, so it is not lost.

Saving preorders

JsonAdaptedPerson saves a customer's preorder in a "preorders" list, which holds one JsonAdaptedPreorder, or none for a customer without a preorder. Each JsonAdaptedPreorder holds its JsonAdaptedItems, and saves the date in YYYY-MM-DD form, the method by its name, and the handover notes. Each JsonAdaptedItem saves each field as a string. A missing fulfilment detail or remark is saved as null. Every item is saved with its quantity.

"preorders" : [ {
  "items" : [ {
    "name" : "Pineapple Tarts",
    "quantity" : "2",
    "status" : "PENDING",
    "remark" : "Less sugar"
  } ],
  "date" : "2026-12-20",
  "method" : "DELIVERY",
  "handoverNotes" : "Call on arrival"
} ]

When the file is loaded, a customer with more than one preorder, a null preorder or item, or a preorder or item field that breaks its rules is reported as invalid data, in the same way as an invalid name or phone number. An item whose "quantity" is missing, null or blank breaks these rules, just like a missing name or status. A preorder without an "items" field loads as a preorder with no items.

Before checking a fulfilment detail, JsonAdaptedPreorder#toModelType() strips surrounding whitespace, treats a blank value as null, and uppercases the method. A hand-edited file is therefore read with the same rules as the preorder command, so "delivery" or "" loads, while a value the command would reject, such as "PICKUP" or "2026-02-30", still makes the file invalid.

Design considerations

Aspect: where the status is kept

  • Alternative 1 (current choice): each Item has its own ItemStatus.
    • Pros: Items that are prepared at different times can be tracked separately.
    • Cons: There is no single status for a customer, so a summary has to look at every item.
  • Alternative 2: one status per Preorder.
    • Pros: Simpler to display and to filter by.
    • Cons: Cannot show that one product is ready while another is not, which is common when a customer orders several products.

Aspect: where the date and method are kept

  • Alternative 1 (current choice): one date, method and set of handover notes per Preorder.
    • Pros: A preorder is handed over in one trip, so its items cannot disagree on when or how.
    • Cons: Items for different days cannot share a preorder. As the data file already saves a list of preorders (see "how preorders are saved" below), a later version can give such a customer a second preorder instead.
  • Alternative 2: a date and method on each Item.
    • Pros: Each product can be handed over on its own day.
    • Cons: The same details are repeated on every item, and changing the date of an order means editing each item.

Aspect: how a quantity is stored

  • Alternative 1 (current choice): a Quantity class.
    • Pros: The rule and its error message are in one place, shared by ParserUtil#parseQuantity and the JSON loader.
    • Cons: One more small class.
  • Alternative 2: a plain int.
    • Pros: Less code.
    • Cons: Each place that creates an item has to repeat the range check.

Aspect: how preorders are saved

  • Alternative 1 (current choice): a list of preorders in the data file, while the model allows only one.
    • Pros: Allowing several preorders per customer later will not change the file format again.
    • Cons: The loader has to reject a list with more than one preorder.
  • Alternative 2: a single "preorder" object.
    • Pros: Matches the model exactly.
    • Cons: Supporting several preorders later would require a change to the saved-data format.

Tracking preorders

track [s/STATUS] displays customers with at least one matching preorder item. Bare track selects active items (PENDING or PREPARED); supplying s/ selects only that status. Status belongs to each item, so a customer with mixed-status items can appear in more than one status search. Customers without a preorder, or with an empty preorder, never match.

Parsing. TrackCommandParser tokenizes the optional s/ prefix, rejects a nonempty preamble, then rejects duplicate status prefixes. With no status prefix, it constructs TrackCommand(Optional.empty()). Otherwise, ParserUtil#parseItemStatus trims surrounding whitespace and accepts PENDING, PREPARED or COMPLETED case-insensitively. An empty or invalid status is rejected before execution. An unsupported prefix after the status, such as track s/pending d/Cake, uses the contextual diagnostic described under Prefix boundaries and error messages. A rejected command leaves the active criteria and displayed results unchanged.

Execution. The sequence diagram below shows TrackCommand#execute for track s/pending. It starts after parsing and shows the command's interactions with the model and the shared item criterion.

  1. createItemCriterion creates an ItemCriterion with no product condition and either the supplied status or the default set {PENDING, PREPARED}.
  2. The command wraps this criterion in a SearchCriteria and calls Model#updateFilteredPersonList. This replaces the previous find or track criteria and filters all stored customers, while keeping the current sort order. The model's observable filtering mechanism is described under Customer search criteria.
  3. Model#getFilteredPersonList returns the matching customers. Each customer appears once, even if several of their items match. Filtering selects customers; their other preorder items remain visible, with matching items highlighted (see Preparation summary and matching-item highlighting).
  4. For each matching customer, the command calls ItemCriterion#getMatchingItems and sums the list sizes into a long total. This counts item entries, including repeated products, rather than adding their quantities.
  5. formatFeedback creates the message for a new CommandResult. Bare track reports N customer(s) with M matching item(s) listed!; an explicit status reports N customer(s) with M matching item(s) for STATUS listed!, including when both counts are zero.

For example, if one customer has two pending Cake entries with quantities 10 and 20, and another has one pending Cookies entry, track s/pending reports 2 customer(s) with 3 matching item(s) for PENDING listed!.

Tracking changes the active search without editing customer or preorder data. Later item changes are re-evaluated against the same criteria automatically, so a customer disappears when their final matching item changes to a nonmatching status or is removed. list clears the criteria and restores the saved customer order.

Design considerations

The alternatives below describe tradeoffs in the current implementation. The choice to store status on each item is covered under Preorders and items.

Aspect: which statuses bare track includes

  • Alternative 1 (current choice): include PENDING and PREPARED items.
    • Pros: Shows orders that still need preparation or handover in one command, while excluding completed work.
    • Cons: Does not distinguish work still to be prepared from work ready for handover. The baker must supply s/PENDING or s/PREPARED to focus on one stage.
  • Alternative 2: include all three statuses.
    • Pros: Gives an overview of every customer with preorder items, including completed work.
    • Cons: Completed orders remain in the default results, making outstanding work harder to identify.

Aspect: how tracking applies its filter

  • Alternative 1 (current choice): use the shared ItemCriterion and SearchCriteria infrastructure.
    • Pros: track and find share item-matching rules. The existing observable search state updates the customer list, criteria badges and item highlighting, and re-evaluates customers after edits.
    • Cons: Changes to the shared item-matching rules can affect both commands, so both need checking when those rules change.
  • Alternative 2: keep a separate tracking predicate and result list.
    • Pros: Tracking rules can change independently of find.
    • Cons: Repeats filtering logic and needs separate handling to keep results and search displays consistent after customer or item changes.

Aspect: what the feedback counts

  • Alternative 1 (current choice): report both customers and matching item entries.
    • Pros: Distinguishes the number of customers to serve from the number of matching entries in their preorders. Repeated products count separately, matching the entries shown on the cards.
    • Cons: The item count does not indicate the number of units to bake; quantities must be read separately.
  • Alternative 2: report only the customer count.
    • Pros: Shorter feedback that corresponds directly to the number of displayed cards.
    • Cons: Hides how many items match when customers have mixed-product or mixed-status preorders.

Preorder item addition and editing

AddItemCommandParser parses a customer index and the required name, quantity and status, with an optional remark. EditItemCommandParser additionally requires i/ITEM_INDEX and constructs an EditItemDescriptor for supplied fields. Both parsers validate the customer-index syntax first, reject duplicate prefixes, check required inputs, and validate item fields in the order name, quantity, status, remark. They reuse the model validators through ParserUtil. ParserUtil trims remarks and handover notes with StringUtil#stripSpaces() rather than String#strip(), which keeps no-break spaces, so a value pasted with one around it is still accepted. Spaces inside the value are kept.

For edititem, failures in i/, q/ and s/ use the contextual diagnostics described under Prefix boundaries and error messages. Names and remarks retain their normal validation and reject forward slashes.

The edit descriptor distinguishes an omitted remark (null), removal (Optional.empty()) and replacement (Optional.of(remark)). The command copies the descriptor defensively. Empty remarks are rejected when adding. Every item has a quantity: additem requires q/, and edititem keeps the existing quantity unless q/ is supplied.

Both commands resolve the customer against the filtered list, copy the immutable item list, and rebuild the preorder and person before calling model.setPerson. Addition appends an item, creating a preorder if absent. Editing validates preorder existence and the full item-list index before replacing only the selected item. No explicit filter reset occurs. User errors produce exceptions before mutation; assertions check already-validated internal assumptions.

The sequence diagram below shows the item replacement performed by EditItemCommand. Addition and deletion use the same immutable preorder/person replacement path, with the item list appended or removed instead.

Success messages use Added/Edited item NUMBER for CUSTOMER: NAME (quantity: QUANTITY, STATUS). Remarks remain visible on the customer card. A missing i/ produces usage instructions. Empty, non-positive or malformed item-index values produce Item index must be a positive integer., unless an unsupported prefix-like token is present, in which case the contextual diagnostic above is used. A syntactically valid positive index beyond the preorder's item count produces The item index provided is invalid. deleteorder still removes the whole preorder; its item-level replacement is a separate feature.

Preorder item deletion

DeleteItemCommandParser parses deleteitem INDEX i/ITEM_INDEX. It validates the customer-index preamble, rejects duplicate i/ prefixes, and parses the required item index using ParserUtil.parseIndex. A missing i/ shows usage instructions. An unsupported prefix after the item-index value, such as deleteitem 1 i/1 x/2, shows Unsupported prefix 'x/' for deleteitem. An item index that is empty, non-positive or malformed shows Item index must be a positive integer. A positive item index beyond the preorder's item count is parsed and later produces The item index provided is invalid. AddressBookParser dispatches deleteitem to this parser.

DeleteItemCommand resolves the customer from model.getFilteredPersonList(), checks that a preorder exists, and validates the item index against its full item list. Invalid input raises ParseException or CommandException before the model changes. Constructor arguments are checked for null, and assertions verify already-validated preconditions in the update helper.

The command copies the immutable item list, removes only the selected position, and constructs a replacement Preorder and Person. It preserves other customer fields and calls model.setPerson without resetting the filter. An empty item list remains wrapped in a preorder. The success message uses the deleted item's original number, name, quantity and status.

The replacement person preserves the customer's postal code. Preorder.withItems preserves the fulfilment date, method and handover notes, including when the final item is removed. Missing optional fields remain absent.

Deleting a preorder

deleteorder INDEX removes a customer's entire preorder, including its items, fulfilment date, method and handover notes. The customer remains stored with the same contact details, postal code and tags.

Parsing. AddressBookParser dispatches the command to DeleteOrderCommandParser, which passes the arguments to ParserUtil#parseIndex and constructs a DeleteOrderCommand. Missing, non-positive or malformed indices, including extra arguments, produce Invalid command format! followed by the command's usage instructions.

Execution. DeleteOrderCommand#execute:

  1. Resolves the customer from model.getFilteredPersonList(), using their currently displayed index. An index beyond this list produces The customer index provided is invalid.
  2. Checks that the customer has a preorder. If not, it throws a CommandException with CUSTOMER has no preorder to delete. before changing the model. A preorder with no items can still be deleted.
  3. Calls createPersonWithoutPreorder to construct a replacement Person with the same name, phone, email, address, postal code and tags, and Optional.empty() for its preorder. Model#setPerson replaces the original customer.
  4. Returns Deleted preorder for CUSTOMER. LogicManager then saves the updated address book through storage.

The command keeps the active search. Replacing the customer re-evaluates the displayed results, so they disappear from track or a search requiring preorder details, but remain in a matching name search. Use list to display all customers again. The preorder is saved as an empty "preorders" list (see Saving preorders).

Design considerations

Aspect: representing a deleted preorder

  • Alternative 1 (current choice): remove the preorder entirely using Optional.empty().
    • Pros: Distinguishes cancellation from an empty preorder awaiting items, and removes the cancelled order's fulfilment details.
    • Cons: Those details must be entered again if the customer places a new preorder.
  • Alternative 2: clear the items but retain an empty preorder and its fulfilment details.
    • Pros: The details can be reused when new items are added.
    • Cons: A cancelled order's date, method and notes could be reused unintentionally. Removing the final item with deleteitem already supports keeping these details (see Preorder item deletion).

Setting fulfilment details: preorder

preorder INDEX [f/DATE] [m/METHOD] [h/HANDOVER_NOTES] sets when and how a customer's preorder is handed over. The three details belong to the whole Preorder, not to its items (see Preorders and items).

Parsing. PreorderCommandParser parses the index with ParserUtil#parsePreambleIndex, rejects repeated prefixes, and fills an EditFulfilmentDescriptor. For each detail, the descriptor records whether its prefix was supplied and, if so, the new value:

  • a prefix with a value, such as f/2026-12-20, sets that detail. The value is checked by ParserUtil#parseFulfilmentDate, #parseFulfilmentMethod (case-insensitive) or #parseHandoverNotes.
  • a prefix with no value, such as h/, clears that detail.
  • a prefix that is not supplied leaves that detail unchanged.

If no prefix is supplied, the parser rejects the command, so a command that changes nothing never reaches the model. An invalid date or method that contains another prefix, such as m/delivery x/1, is reported as an unsupported prefix (see Prefix boundaries and error messages). Handover notes are free text, so they keep such text.

Execution. The sequence diagram below shows PreorderCommand#execute for preorder 1 m/delivery. Parsing is the same as for delete (see the Logic component), so the diagram starts at execute(m).

  1. The command gets the customer at INDEX in the displayed list, or throws a CommandException if the index is out of range.
  2. If the customer has no preorder and the command only clears details, it returns CUSTOMER has no preorder, so there is nothing to clear. No changes made. and the model is not changed.
  3. Otherwise, it starts from the customer's preorder, or from an empty Preorder if they have none. createUpdatedPreorder builds a new Preorder with the same items, taking each detail from the descriptor if it was supplied and from the current preorder if not.
  4. createPersonWithPreorder builds a new Person with the same contact details, postal code and tags, and the updated preorder. Model#setPerson replaces the customer. The active search is kept.
  5. The success message shows all three details through Messages#formatFulfilmentDetails, using Not scheduled, Not set and None for missing ones. If the supplied date is before today, a second line adds Note: DATE is in the past.

Design considerations

Aspect: how to clear a detail

  • Alternative 1 (current choice): an empty prefix clears that detail, e.g. preorder 1 h/.
    • Pros: One command both sets and clears details, so there is one less command to learn. It works the same way as removing a remark with an empty r/ in edititem.
    • Cons: The descriptor has to tell "not supplied" apart from "supplied but empty", which needs a flag per detail.
  • Alternative 2: a separate clearpreorder INDEX command.
    • Pros: Clearing is explicit.
    • Cons: Another command word. It clears all three details at once, so clearing only the notes still needs another way.

Aspect: dates in the past

  • Alternative 1 (current choice): accept the date and add a note.
    • Pros: A baker may record an order that has already been handed over, or fix an old record. Blocking these would be overzealous validation.
    • Cons: A mistyped year is saved; the baker has to notice the note.
  • Alternative 2: reject past dates.
    • Pros: Catches some typing mistakes.
    • Cons: Blocks legitimate records, and depends on the computer's clock being right.

Aspect: what preorder does for a customer without a preorder

  • Alternative 1 (current choice): create a preorder with no items.
    • Pros: The baker can record the date and method first and add items later, in any order.
    • Cons: An empty preorder must be handled by track, find, sort date and the summaries.
  • Alternative 2: require an item first.
    • Pros: Every preorder has at least one item.
    • Cons: The baker has to enter the order in a fixed sequence.

Grouping customers by postal code: group postal

group postal orders the currently displayed customers by postal code and shows a heading for each two-digit postal prefix. It keeps the active search criteria and the saved customer order.

Parsing. LogicManager#execute passes the input to AddressBookParser#parseCommand, which routes the lowercase command word group to GroupPostalParser#parse. The parser accepts only postal, ignoring case and surrounding spaces, and returns a GroupPostalCommand. Missing or extra arguments, including c/ parameters, produce the invalid-command-format message followed by GroupPostalCommand.MESSAGE_USAGE.

Execution. GroupPostalCommand#execute calls Model#updatePersonListComparator(GroupPostalCommand.POSTAL_COMPARATOR) and returns Customers grouped by postal code. The comparator is defined in GroupPostalCommand.java.

getPostalGroupKey returns the first two digits using substring(0, 2). Within each prefix, customers are ordered by the complete six-digit code, then by name ignoring case. PostalCode stores six digits as a string, preserving leading zeros. Every Person must have a valid, non-null postal code, so there is no missing-code group (see Customer search criteria for the separate rules for stored codes and search prefixes).

ModelManager keeps the data in AddressBook, selects customers through a FilteredList<Person>, and wraps that in a SortedList<Person>. ModelManager#updatePersonListComparator changes only the sorted view's comparator; Model#getFilteredPersonList() exposes this view to the UI and index-based commands. The grouping command never replaces the active criteria or reorders the backing list. After execution, LogicManager#executeAndSave saves model.getAddressBook(), so the full saved list retains its order even though the displayed list is grouped.

Display. MainWindow supplies the displayed view to PersonListPanel. Its PersonListViewCell#updateItem adds a POSTAL PREFIX XX label above the PersonCard when the customer is first in the displayed list or their prefix differs from the preceding displayed customer's prefix. Headings are enabled only when the list is a SortedList using the exact GroupPostalCommand.POSTAL_COMPARATOR instance. Each heading is part of a customer cell, not a separate list entry, so the card's one-based index remains getIndex() + 1.

The panel refreshes cells when the list or its comparator changes. The comparator listener also adds or removes headings when the customers were already in the required order and no list permutation occurs. Customer edits refresh the sorted view and headings, so changing a postal code can move a customer and change their index.

find and track replace the criteria but keep postal ordering; only matching customers are grouped. Empty results still return the normal success message, with no customer cards or headings. sort date replaces the postal comparator and removes the customer-list headings. list clears the criteria and comparator; a confirmed clear also resets both. Restarting creates a model without a comparator, displaying all saved customers in saved order. See Sorting by fulfilment date for the shared ordering/reset mechanism.

The command neither selects outstanding deliveries nor calculates routes or group totals. The side panel's Delivery preparation summary derives its own stops and prefix headings independently.

Design considerations

Aspect: grouping a view rather than the saved list

The current choice uses the same sorted view as sort date, keeping searching and ordering separate. It preserves the saved order for list and restart; reordering AddressBook instead would persist an unintended order change. The trade-off is that displayed indexes can change after edits. Index-based commands must continue to use the displayed view (see the date-sort design discussion).

Aspect: prefix headings and grouping state

The fixed two-digit prefix gives one heading to codes with the same first two digits, while the full-code/name comparator makes the order within that heading deterministic. String values preserve leading zeros; numeric conversion would discard them. This is a grouping convention, not validation that an address exists or a delivery-route calculation.

Using the shared comparator instance to enable headings avoids a separate grouping flag that could disagree with the ordering. The trade-off is coupling between GroupPostalCommand and PersonListPanel: a replacement or wrapped comparator must preserve this detection or deliberately replace it. An explicit ordering-mode property would make that state independent of comparator identity, but would need to stay synchronized with sorting and reset commands.

Sorting by fulfilment date: sort date

sort date orders the displayed customers by the date of their preorder, earliest first.

ModelManager wraps its FilteredList<Person> in a JavaFX SortedList<Person>, and Model#getFilteredPersonList() returns the sorted view. The UI and every index-based command use this view, so the index a command uses is always the number shown on screen. Model#updatePersonListComparator(comparator) sets the comparator of the sorted view; null restores the saved order.

SortCommandParser accepts only the word date, ignoring case and surrounding spaces. SortCommand#execute calls updatePersonListComparator(SortCommand.DATE_COMPARATOR), which orders customers by:

  1. fulfilment date, earliest first. Customers with no preorder, or a preorder with no date, use LocalDate.MAX, so they are listed last.
  2. name, ignoring case, for customers with the same date (or no date).

The comparator lives in the model, separately from the search criteria, so:

  • find and track change which customers are shown but keep the sort.
  • group postal sets its own comparator, which replaces the date sort, and sort date replaces the grouping.
  • list and clear set the comparator to null, which restores the saved order.
  • when a command changes a customer, such as preorder 1 f/2026-12-24, the SortedList moves them to their new place, so their index may change.
  • the sort is not saved, so the app starts in the saved order.

Design considerations

Aspect: how to sort

  • Alternative 1 (current choice): sort a view of the list with a comparator.
    • Pros: The data file keeps its order, so sorting never changes saved data. Searching and sorting are kept apart, and each can change without resetting the other.
    • Cons: Indices can change after an edit, as described above; the UG warns about this.
  • Alternative 2: reorder the customers in AddressBook.
    • Pros: The order would survive a restart.
    • Cons: Sorting would rewrite the data file, and list could no longer show the order in which customers were added.

Tagging customers: tag and untag

tag INDEX t/TAG adds one tag to the customer at INDEX in the displayed list, and untag INDEX t/TAG removes one.

Parsing. Both commands take the same input, so TagCommandParser and UntagCommandParser share two helpers: ParserUtil#parsePreambleIndex for the index, and ParserUtil#parseSingleTag, which requires exactly one t/ and checks that the tag is one word of letters and digits, at most 30 characters. The index is checked first, so tag 0 t/! reports the index error.

Execution. Both commands follow the same pattern as delete, shown in the sequence diagram under Logic component. They get the customer from the displayed list, build a new Person with the updated tags and the same contact details, postal code and preorder, and replace the customer with Model#setPerson, keeping the active search and sort. If the customer already has the tag, tag shows CUSTOMER already has tag [TAG]. No changes made. and leaves the model unchanged.

Design considerations

Aspect: where tags are changed

  • Alternative 1 (current choice): separate tag and untag commands; add and edit do not take tags.
    • Pros: Adding a tag never removes the others. In AB3, edit 1 t/vip replaced all of a customer's tags.
    • Cons: Two more command words.
  • Alternative 2: t/ in add and edit, as in AB3.
    • Pros: Fewer commands.
    • Cons: Adding one tag means retyping all the others.

Aspect: case of tags

  • Alternative 1 (current choice): Tag#equals and Tag#hashCode ignore case.
    • Pros: VIP and vip cannot both be on one customer, untag 1 t/vip removes VIP, and find t/ follows the same rule.
    • Cons: A tag keeps the capitalisation it was first typed with.
  • Alternative 2: compare case-insensitively only in the tag commands.
    • Pros: Smaller change to Tag.
    • Cons: Other commands could disagree about which tags are the same.

Aspect: adding a tag the customer already has

  • Alternative 1 (current choice): show a note and change nothing.
    • Pros: The customer already has the tag the user wanted, so nothing went wrong, and repeating a command does no harm.
    • Cons: A user who picked the wrong customer is not stopped as firmly.
  • Alternative 2: reject the command with an error.
    • Pros: The mistake stands out more.
    • Cons: Treats a harmless request as a failure.

Glossary

  • Active order: A pre-order with at least one item whose fulfilment status is PENDING or PREPARED
  • Archived customer: A customer hidden from the active customer list but kept, so that it can be restored for a future seasonal campaign
  • Customer: A person whose contact and delivery details are stored in LeBake, represented by the Person class in the code
  • Duplicate customer: A customer with the same name as an existing customer, ignoring case and extra spaces (phone number, email and address are not compared)
  • Fulfilment date: The date a pre-order is to be delivered or collected, shared by all items in the pre-order
  • Fulfilment method: How a pre-order is handed over, which is DELIVERY (the baker brings it to the customer) or COLLECTION (the customer picks it up)
  • Fulfilment status: The stage an item in a pre-order has reached, which is PENDING (recorded but not ready), PREPARED (ready for collection or delivery), or COMPLETED (collected or delivered). Each item has its own status, represented by ItemStatus in the code; a pre-order has no overall status
  • Handover notes: A short note about handing over a pre-order, such as "Call on arrival" or "Collect from side gate", shared by all items in the pre-order
  • Item: One product in a pre-order, with its name, quantity, fulfilment status and an optional remark
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Postal area: A group of nearby addresses that share the same leading digits of their postal code, used to group deliveries
  • Pre-order: An order placed in advance for a later collection or delivery, made up of the items the customer ordered, with each customer having at most one current pre-order
  • Private contact detail: A contact detail that is not meant to be shared with others
  • Seasonal campaign: A period of high order demand tied to an occasion, such as Chinese New Year or Christmas
