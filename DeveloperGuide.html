Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, SearchCriteriaDisplay, PersonListPanel, SidePanel and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects and structured search criteria.

MainWindow lays out two columns. The left one holds the CommandBox, ResultDisplay, SearchCriteriaDisplay and PersonListPanel, and keeps at least 450 px so that cards still wrap whole words. The right one is the SidePanel, at least 300 px wide, which shows one long output at a time: the HelpPanel after help, the ProductSummaryPanel while it is visible during a product search, and the DeliverySummaryPanel otherwise. MainWindow shows help when a CommandResult asks for it, and returns the panel to the summaries after the next successful command. A window narrower than 900 px gets the :compact pseudo-class, which DarkTheme.css uses to tighten the gaps around the customer list.

MainWindow owns one SearchCriteriaDisplay, places it above the customer list and supplies Logic.activeSearchCriteriaProperty(). The display renders the current value immediately and observes criteria changes directly, including searches with identical results. It delegates formatting to SearchCriteriaFormatter, which creates an immutable SearchCriteriaSummary. The display uses the summary's heading and complete criterion labels to render its badges in predictable order. These dependencies are shown with dashed arrows in the UI diagram. Formatting stays separate from matching and does not parse diagnostic toString() output.

PostalCodeCriterion.getPostalCodePrefix() exposes the immutable search digits for a Postal badge, preserving leading zeros and the supplied prefix length. Postal badges are ordered after Address and before Tag badges.

ItemCriterion exposes its stripped display product name and immutable accepted statuses. The formatter keeps the capitalization typed by the user and both conditions in one Item badge after customer badges, reflecting same-item matching. All statuses on a product criterion display as Any status; subsets display their readable labels joined by or in fulfilment order. A criterion without a product uses Item status, retaining the status-only search and tracking labels. An empty status set displays None, so a criterion matching no items is still visible.

FulfilmentDateCriterion.getDate() and FulfilmentMethodCriterion.getMethod() expose their immutable matching values. Date badges reuse FulfilmentDate.toDisplayString() for English dates such as 22 Oct 2026; method badges show Delivery or Collection. Handover-note badges use the normalized query from TextContainsCriterion. The complete display order is Name, Phone, Email, Address, Postal, Tag, Item (or Item status), Date, Method and Handover notes, independent of prefix order or the model's unordered criteria set.

The display uses a FlowPane of read-only labels. Badges wrap onto additional rows without a row limit, and each badge is limited to the available width so long values wrap inside it. Its preferred-height measurement also accounts for wrapping when FlowPane measures a row without supplying a width. Empty searches hide the badge container and show only Showing: All customers; active searches show Filters · Match all. No focus request is made during an update, and the display cannot receive mouse input or keyboard focus.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Prefix boundaries and error messages

ArgumentTokenizer recognizes only the prefixes supplied by a command parser, with whitespace before each prefix. A supported prefix ends the preceding value. Unsupported prefix-like text stays in the current value or preamble. The tokenizer preserves conventional c/o text inside an address instead of treating it as a postal-code prefix. Quotation marks and backslashes do not escape supported prefixes.

Three parsers refine errors from constrained fields using ParserUtil.findUnsupportedPrefix:

Parser Fields with contextual prefix diagnostics
DeleteItemCommandParser Item index (i/)
EditItemCommandParser Item index (i/), quantity (q/) and status (s/)
TrackCommandParser Status (s/)

Each field is validated normally first. If parsing fails, the helper finds the first token matching \s([A-Za-z]+/) whose prefix is absent from that command's supported-prefix list. It preserves the prefix's case and returns an Optional<Prefix>. The parser formats Messages.MESSAGE_UNSUPPORTED_PREFIX with the offending prefix and command name, for example Unsupported prefix 'd/' for track. If no unsupported prefix is found, the original field constraint message is used. A slash embedded without a preceding whitespace boundary does not trigger this diagnostic. Customer-index and duplicate-prefix checks retain their earlier precedence.

This is an error-message refinement rather than a global rejection rule. Item names, remarks and handover notes can contain unsupported prefix-like text, subject to their model constraints. Do not apply the helper to free-text values or scan the complete command before field validation: text such as Pack w/o nuts x/2 can be intentional. FindCommandParser has a separate, stricter rule that rejects unsupported letter-based prefixes throughout the arguments, including text criteria. Its behaviour is unchanged by these contextual diagnostics.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores each customer's preorder, if any, as a Preorder holding the Items they ordered (see Preorders and items).
  • retains one active SearchCriteria in ModelManager to select which customers appear in the filtered list (see Customer search criteria).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Customer search criteria

The seedu.address.model.search package provides reusable search predicates. FindCommandParser constructs a SearchCriteria from prefixed customer and item fields, and FindCommand applies it through the existing model filtering API.

ModelManager keeps the active SearchCriteria in a ReadOnlyObjectWrapper. The filtered list's predicate is bound to this value, so replacing the criteria updates both the search state and the results. All filtering calls supply structured SearchCriteria, rather than an arbitrary predicate. getActiveSearchCriteria() returns the current immutable value, while activeSearchCriteriaProperty() exposes read-only observation through both Model and Logic. Observers can detect a different search even when its results are identical. This state is kept in memory and is not saved with customer data.

Each successful find or track replaces the active criteria. list applies SEARCH_CRITERIA_SHOW_ALL_PERSONS, an empty search, to reset the state and show every customer. Rejected commands leave the active criteria unchanged. find and track use the immutable ItemCriterion for item matching. It accepts a customer when any single item satisfies both its optional product name and accepted statuses. Customers without a preorder or with an empty preorder never match item criteria.

Customer changes preserve the active criteria. addPerson inserts into the observable backing list, while setPerson replaces an immutable customer; FilteredList re-evaluates the affected entry automatically. A new customer is displayed only if they match, and an edited customer disappears when they stop matching. Tag and preorder updates follow the same replacement path. Commands resolve their target from the displayed list before making changes, and later commands use the resulting displayed indexes. Rejected updates preserve both criteria and results.

SearchCriteria implements Predicate<Person> and combines zero or more PersonCriterion objects using AND. A customer must match every criterion. An empty search matches every customer. The constructor defensively copies its criteria into an immutable set, so changing the source collection cannot change an existing search. Criterion order and duplicate conditions do not affect matching or equality; rejecting repeated CLI prefixes is the parser's responsibility.

The following diagram shows the criteria structure and its current implementations:

For example, the following predicate matches customers whose name contains Alice Tan and who have the tag regular:

SearchCriteria criteria = new SearchCriteria(List.of(
        new TextContainsCriterion(TextContainsCriterion.Field.NAME, "Alice Tan"),
        new TagCriterion(new Tag("regular"))));

TextContainsCriterion supports name, phone, email and address fields. It strips surrounding query whitespace and matches the entire query as a case-insensitive substring using locale-independent case normalization. Internal spacing and punctuation remain significant. Queries must be nonblank, but may be fragments such as 8123 or example.com; they do not use the validation rules for creating complete contact fields. TagCriterion accepts a validated Tag and uses its complete, case-insensitive equality rule.

FulfilmentDateCriterion and FulfilmentMethodCriterion inspect the optional shared fields on Preorder, independently of its items. TextContainsCriterion.Field.HANDOVER_NOTES reads Preorder.getHandoverNotes() and uses the existing case-insensitive substring matcher. Missing preorders or missing requested fields do not match; empty preorders with matching fields do. Searches for handover notes do not inspect item remarks.

The f/ and m/ values are parsed through ParserUtil.parseFulfilmentDate and parseFulfilmentMethod. Dates must be real calendar dates in YYYY-MM-DD format; methods are stripped and normalized with Locale.ROOT to DELIVERY or COLLECTION. Invalid values produce the corresponding model constraint message. The shared PREFIX_HANDOVER_NOTES constant defines h/ for handover notes. These queries follow existing text search rules: surrounding whitespace is stripped, while internal spacing and punctuation remain significant. Blank values, repeated prefixes and unsupported prefixes retain the shared parser's error handling.

All find searches require a supported prefix, including n/ for names. Unprefixed searches and bare preambles are rejected; find Alice m/delivery must use find n/Alice m/delivery instead.

PostalCodeCriterion accepts a search prefix stored as a string. FindCommandParser strips surrounding whitespace from the c/ value and validates it using PostalCodeCriterion.isValidPrefix, which accepts one to six ASCII digits ([0-9]{1,6}). Blank values produce the existing invalid-command-format error; other invalid values produce PostalCodeCriterion.MESSAGE_CONSTRAINTS. The criterion also validates its constructor argument and matches using postalCode.value.startsWith(postalCodePrefix). Leading zeros remain significant, a six-digit query is an exact match, and customers whose postal code is null do not match. This criterion joins the same SearchCriteria collection as other conditions, so find n/Alice c/53 requires both conditions and each new find replaces the previous criteria.

Customer-record validation remains separate: add and edit continue to use ParserUtil.parsePostalCode and PostalCode, which require exactly six digits. A valid search prefix is never used as a customer's stored postal code.

To add a search condition with different matching rules, implement PersonCriterion and include it in a SearchCriteria collection. The implementation must be immutable and provide value-based equals and hashCode. CLI prefixes belong in the parser, not in the criteria. Add the prefix to FindCommandParser's supported-prefix list and construct its criterion there. The parser accepts each supported prefix once, requires a prefix before the first value, rejects blank or unsupported parameters, and validates tags using ParserUtil.parseTag and postal search prefixes using PostalCodeCriterion.isValidPrefix. It recognizes prefixes at whitespace boundaries without collapsing internal query spacing, including c/o inside an address. FindCommand passes SearchCriteria directly to Model.updateFilteredPersonList, which replaces the active criteria on the list backed by the full address book. There is no need to filter the previous search's results or execute another search command as an intermediate step. When adding a criterion type, also add its label and display position to SearchCriteriaFormatter, with formatter tests. Existing display bindings and wrapping then apply automatically. Keep conditions on the same item together in one criterion and one badge.

FindCommandParser combines d/ (PREFIX_DETAILS) and s/ into one ItemCriterion. Separate predicates for "has this product" and "has this status" would incorrectly allow different items to satisfy the conditions. Product names match completely after stripping surrounding whitespace and normalizing case with Locale.ROOT; internal spacing and punctuation remain significant. The criterion also retains the stripped input name for display; matching, equality and hash codes use the normalized name. Status input is validated with ParserUtil.parseItemStatus.

The parser supplies EnumSet.allOf(ItemStatus.class) when s/ is omitted. This is deliberate: an empty status set in ItemCriterion matches nothing, rather than meaning "any status". An absent product name accepts any product. Bare track supplies only PENDING and PREPARED; explicit track s/STATUS and find s/STATUS produce equivalent item criteria. Each new command still replaces the previous search, rather than accumulating conditions.

ItemCriterion.matches(Item) is the shared item-level check. getMatchingItems(Person) returns an unmodifiable list that preserves item order and duplicate entries. TrackCommand counts filtered customers once each, then sums the sizes of their matching-item lists using a long total. It counts item entries, not quantities, including migrated items without quantities. Explicit status feedback retains the requested status even when both counts are zero.

The criterion rejects null arguments, null status elements and blank product queries, and defensively copies the status set. Its normalized conditions define value equality and hash codes for observable search state. Date/method and postal conditions remain separate customer criteria because they describe the preorder or customer rather than an individual item.

Preparation summary and matching-item highlighting

ProductPreparationSummary.from creates an immutable snapshot from the filtered customers and a product ItemCriterion. It reuses ItemCriterion.matches, retaining matching entries in customer/item order, including duplicates. Each MatchingItem retains its customer and original one-based item number for remark attribution. Customer count is distinct, item count counts entries, and quantity is summed using long. Missing quantities from migrated data are counted separately so that a known subtotal is never presented as a complete total. Constructors reject null inputs and invalid item references; collections are defensively copied.

MainWindow puts ProductSummaryPanel in the SidePanel. The summary listens to both the filtered customer list and Logic.activeSearchCriteriaProperty(), so changing criteria refreshes it even when the same customers remain visible. Its criteria invalidation listener also refreshes the heading for capitalization-only changes, which are equal for filtering purposes. It is visible and managed only when a product criterion exists. Updates recompute the snapshot, including zero results. Labels wrap inside a focusable scroll pane, whose key handler supports arrows, Page Up/Down and Home/End with scroll values clamped to the valid range.

PersonListPanel also refreshes its cells when active criteria change. Each PersonCard receives the current criteria and reuses the item matcher to add the matching-item style, a yellow box. It keeps all items, original numbering and status styles. Status-only criteria (including track) also highlight matching items; criteria without item conditions produce no highlights. The customer list uses native JavaFX keyboard navigation and selects its first entry when focused without an existing selection.

Delivery preparation summary

DeliveryPreparationSummary takes a snapshot of the current displayed customer results. It reuses ItemCriterion with no product condition and statuses PENDING and PREPARED, then requires the preorder's method to be DELIVERY. It counts customers, not matching items. Collection, unset methods, empty wrappers and completed-only preorders are excluded. Missing postal codes remain represented by one additional group; dates and notes may be unset without excluding an otherwise outstanding delivery. The immutable snapshot orders contacts by postal code and name, without mutating the address book or the active search criteria.

MainWindow puts a DeliverySummaryPanel in the SidePanel. The panel observes the existing Logic.getFilteredPersonList() observable view and rebuilds its snapshot when results or customer records change. It reuses GroupPostalCommand.getPostalGroupKey for contact headings and FulfilmentDate.toDisplayString for dates. Names, phones, addresses, postal codes and shared handover notes are shown in a keyboard-scrollable area with wrapped text. Missing dates display Not scheduled; absent handover notes display Handover notes: None. The panel stays installed and visible when there are no outstanding deliveries, showing zero totals and No outstanding deliveries in the current results. The UI tests cover exclusion of ineligible preorders, one contact per customer with multiple outstanding items, postal headings, and layout at the minimum FXML window dimensions.

This adds a derived model snapshot and a UI part within the existing Model/Logic/UI boundaries. It does not introduce stored summary state or change the fulfilment fields, JSON schema, customer reconstruction, or grouping command.

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)
  • saves preorders through JsonAdaptedPreorder and JsonAdaptedItem, and reads preorders saved by v1.3 through JsonAdaptedLegacyPreorder (see Saving preorders).

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Preorders and items

A customer's preorder records the products they ordered and how they will be handed over. Each customer has at most one Preorder, and each Preorder holds the customer's Items in the order they were added.

  • Person stores its preorder as an Optional<Preorder>, which is empty for a customer without one.
  • Preorder keeps an unmodifiable copy of its items and may have none yet. The number shown before an item on the customer's card is its position in this list, starting from 1.
  • Preorder also has an optional FulfilmentDate, FulfilmentMethod (DELIVERY or COLLECTION) and HandoverNotes, such as "Call on arrival". They belong to the whole preorder, so all of its items are handed over together. Preorder#withItems() keeps them when a command changes the items.
  • Item has an ItemName of up to 200 characters, an ItemStatus, and an optional Quantity and Remark. A Quantity is a whole number from 1 to 999, and a Remark is a special request of up to 100 characters.
  • New items always have a quantity. Item#getQuantity() is empty only for items converted from v1.3 data, as described under "Loading v1.3 data" below.
  • ItemStatus belongs to each item, so a customer can have one item PREPARED while another is still PENDING. There is no overall status for a customer or a preorder. track matches a customer when any item has one of the requested statuses.

Preorder and Item are immutable. A command that changes a customer creates a new Person and replaces the old one through Model#setPerson. Commands that do this for other reasons, such as edit, tag and untag, pass the existing preorder to the new Person, so it is not lost.

Saving preorders

JsonAdaptedPerson saves a customer's preorder in a "preorders" list, which holds one JsonAdaptedPreorder, or none for a customer without a preorder. Each JsonAdaptedPreorder holds its JsonAdaptedItems, and saves the date in YYYY-MM-DD form, the method by its name, and the handover notes. Each JsonAdaptedItem saves each field as a string. A missing fulfilment detail or remark, or the missing quantity of a converted item, is saved as null.

"preorders" : [ {
  "items" : [ {
    "name" : "Pineapple Tarts",
    "quantity" : "2",
    "status" : "PENDING",
    "remark" : "Less sugar"
  } ],
  "date" : "2026-12-20",
  "method" : "DELIVERY",
  "handoverNotes" : "Call on arrival"
} ]

When the file is loaded, a customer with more than one preorder, a null preorder or item, or a preorder or item field that breaks its rules is reported as invalid data, in the same way as an invalid name or phone number. A preorder without an "items" field loads as a preorder with no items.

Loading v1.3 data

LeBake v1.3 saved a single "preorder" object with free-text "details" and one "status". JsonAdaptedPerson still reads that field through JsonAdaptedLegacyPreorder, which turns it into a preorder with one item named after the old details, with the old status. v1.3 did not record a quantity, and guessing one from the details could be wrong, so the item has no quantity and its card shows Qty needed. The converted preorder has no date, method or handover notes, as v1.3 had none. The old field is never written back, so the next save stores the customer in the current format.

Design considerations

Aspect: where the status is kept

  • Alternative 1 (current choice): each Item has its own ItemStatus.
    • Pros: Items that are prepared at different times can be tracked separately.
    • Cons: There is no single status for a customer, so a summary has to look at every item.
  • Alternative 2: one status per Preorder.
    • Pros: Simpler to display and to filter by.
    • Cons: Cannot show that one product is ready while another is not, which is common when a customer orders several products.

Aspect: where the date and method are kept

  • Alternative 1 (current choice): one date, method and set of handover notes per Preorder.
    • Pros: A preorder is handed over in one trip, so its items cannot disagree on when or how.
    • Cons: Items for different days cannot share a preorder. As the data file already saves a list of preorders (see "how preorders are saved" below), a later version can give such a customer a second preorder instead.
  • Alternative 2: a date and method on each Item.
    • Pros: Each product can be handed over on its own day.
    • Cons: The same details are repeated on every item, and changing the date of an order means editing each item.

Aspect: how a quantity is stored

  • Alternative 1 (current choice): a Quantity class.
    • Pros: The rule and its error message are in one place, shared by ParserUtil#parseQuantity and the JSON loader. An item without a quantity is an empty Optional<Quantity>, the same way an item without a remark is an empty Optional<Remark>.
    • Cons: One more small class.
  • Alternative 2: a plain int.
    • Pros: Less code.
    • Cons: Each place that creates an item has to repeat the range check, and a missing quantity needs a special value such as 0.

Aspect: how preorders are saved

  • Alternative 1 (current choice): a list of preorders in the data file, while the model allows only one.
    • Pros: Allowing several preorders per customer later will not change the file format again.
    • Cons: The loader has to reject a list with more than one preorder.
  • Alternative 2: a single "preorder" object, as in v1.3.
    • Pros: Matches the model exactly.
    • Cons: Supporting several preorders later would need another conversion of saved data.

Preorder item addition and editing

AddItemCommandParser parses a customer index and the required name, quantity and status, with an optional remark. EditItemCommandParser additionally requires i/ITEM_INDEX and constructs an EditItemDescriptor for supplied fields. Both parsers validate the customer-index syntax first, reject duplicate prefixes, check required inputs, and validate item fields in the order name, quantity, status, remark. They reuse the model validators through ParserUtil.

For edititem, failures in i/, q/ and s/ use the contextual diagnostics described under Prefix boundaries and error messages. Names and remarks retain their normal validation and preserve unsupported prefix-like text.

The edit descriptor distinguishes an omitted remark (null), removal (Optional.empty()) and replacement (Optional.of(remark)). The command copies the descriptor defensively. Empty remarks are rejected when adding. New items must have quantities; editing preserves a migrated missing quantity unless a quantity is supplied.

Both commands resolve the customer against the filtered list, copy the immutable item list, and rebuild the preorder and person before calling model.setPerson. Addition appends an item, creating a preorder if absent. Editing validates preorder existence and the full item-list index before replacing only the selected item. No explicit filter reset occurs. User errors produce exceptions before mutation; assertions check already-validated internal assumptions.

The sequence diagram below shows the item replacement performed by EditItemCommand. Addition and deletion use the same immutable preorder/person replacement path, with the item list appended or removed instead.

Success messages use Added/Edited item NUMBER for CUSTOMER: NAME (quantity: QUANTITY, STATUS). For migrated items without a quantity, the quantity portion is quantity needed; the card shows Qty needed. Remarks remain visible on the customer card. A missing i/ produces usage instructions. Invalid item-index values use the contextual diagnostics above, with Item index must be a positive integer. as the fallback message. deleteorder still removes the whole preorder; its item-level replacement is a separate feature.

Preorder item deletion

DeleteItemCommandParser parses deleteitem INDEX i/ITEM_INDEX. It validates the customer-index preamble, rejects duplicate i/ prefixes, and parses the required item index using ParserUtil.parseIndex. A missing i/ shows usage instructions. An unsupported prefix after the item-index value, such as deleteitem 1 i/1 x/2, shows Unsupported prefix 'x/' for deleteitem. Other empty or invalid item-index values show Item index must be a positive integer. AddressBookParser dispatches deleteitem to this parser.

DeleteItemCommand resolves the customer from model.getFilteredPersonList(), checks that a preorder exists, and validates the item index against its full item list. Invalid input raises ParseException or CommandException before the model changes. Constructor arguments are checked for null, and assertions verify already-validated preconditions in the update helper.

The command copies the immutable item list, removes only the selected position, and constructs a replacement Preorder and Person. It preserves other customer fields and calls model.setPerson without resetting the filter. An empty item list remains wrapped in a preorder. The success message uses the deleted item's original number, name, quantity and status; missing quantities are displayed as blank values.

The replacement person preserves the customer's postal code. Preorder.withItems preserves the fulfilment date, method and handover notes, including when the final item is removed. Missing optional fields remain absent.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

The redo command does the opposite — it calls Model#redoAddressBook(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the address book to that state.

Note: If the currentStatePointer is at index addressBookStateList.size() - 1, pointing to the latest address book state, then there are no undone AddressBook states to restore. The redo command uses Model#canRedoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Step 6. The user executes clear, which calls Model#commitAddressBook(). Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow.

Glossary

  • Active order: A pre-order with at least one item whose fulfilment status is PENDING or PREPARED
  • Archived customer: A customer hidden from the active customer list but kept, so that it can be restored for a future seasonal campaign
  • Customer: A person whose contact and delivery details are stored in LeBake, represented by the Person class in the code
  • Duplicate customer: A customer with the same name as an existing customer, ignoring case and extra spaces (phone number, email and address are not compared)
  • Fulfilment status: The stage an item in a pre-order has reached, which is PENDING (recorded but not ready), PREPARED (ready for collection or delivery), or COMPLETED (collected or delivered). Each item has its own status, represented by ItemStatus in the code; a pre-order has no overall status
  • Item: One product in a pre-order, with its name, quantity, fulfilment status and an optional remark
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Postal area: A group of nearby addresses that share the same leading digits of their postal code, used to group deliveries
  • Pre-order: An order placed in advance for a later collection or delivery, made up of the items the customer ordered, with each customer having at most one current pre-order
  • Private contact detail: A contact detail that is not meant to be shared with others
  • Seasonal campaign: A period of high order demand tied to an occasion, such as Chinese New Year or Christmas
